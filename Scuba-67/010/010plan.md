# แผนทางเทคนิค: UC10 - ออกรายงานยอดขายและกระทบยอด

## 1. สรุปแนวทาง
1. ฟีเจอร์นี้สร้างหน้าจอรายงานยอดขายและการเงินสำหรับเจ้าของร้าน/ผู้จัดการให้เลือกช่วงเวลาแบบ Date Range Picker และตรวจสอบยอดขายรวมตามช่องทางชำระเงินหลัก 2 แบบ ได้แก่ เงินสดและ QR Code (UC10 Main Flow 1-3, ASM-01, ASM-04)
2. ระบบจะประมวลผลข้อมูลผ่าน Reporting Aggregation API โดยใช้สูตร `ยอดขายเงินสด + ยอด QR Code - ค่าธรรมเนียมระบบ = ยอดรับสุทธิ` และยืนยันว่าคำนวณมีความถูกต้อง 100% โดยไม่มีข้อผิดพลาดทศนิยม (UC10 Main Flow 3, ASM-02)
3. การคำนวณยอดตัดสต๊อกจะใช้ฐานข้อมูลการขายที่สำเร็จในช่วงเวลานั้นและคำนวณตามสูตร BOM เพื่อให้รายงานสะท้อนปริมาณและรายการวัตถุดิบที่ถูกหักลบออกจากคลังจริง (UC10 Main Flow 3, ASM-03)
4. ระบบจะส่งออกไฟล์ PDF และ Excel (.xlsx) ในรูปแบบตารางมาตรฐานสำหรับงานบัญชี โดยมีข้อมูลสรุปยอดขายรวม, ช่องทางชำระเงิน, ค่าธรรมเนียม, ยอดสุทธิ, และยอดตัดสต๊อกให้ตรงกับ Dashboard (UC10 Main Flow 4, ASM-05)
5. หากยอดเงินไม่ตรงกับ Statement ธนาคาร ระบบจะไม่ลบหรือยกเลิกรายการ แต่จะแยกข้อมูลไปไว้ในรายงาน Discrepancy / Pending Log เพื่อให้เจ้าของร้านตรวจสอบต่อไป (UC10 Alternative 3a, ASM-06)

## 4. API / หน้าจอ

- `GET /api/reports/sales-summary?from=&to=&type=` ส่งกลับสรุปยอดขายตามช่วงเวลาที่ผู้ใช้เลือก พร้อมแสดงผลแบ่งตามเงินสดและ QR Code (UC10 Main Flow 2-3; ASM-01, ASM-04)
- `POST /api/reports/aggregation/calculate` รับช่วงเวลาและแหล่งข้อมูลยอดขายเพื่อคำนวณ `ยอดขายเงินสด + ยอด QR Code - ค่าธรรมเนียมระบบ = ยอดรับสุทธิ` และคืนค่า net_sales ที่ถูกต้อง 100% (UC10 Main Flow 3; ASM-02)
- `GET /api/reports/stock-deduction?from=&to=` ส่งกลับรายการตัดสต๊อกและปริมาณวัตถุดิบที่หักออกจากคลังจริงตามสูตร BOM (UC10 Main Flow 3; ASM-03)
- `GET /api/reports/discrepancy` ส่งกลับรายการที่ไม่ตรงกับ Statement ธนาคาร เพื่อแสดงในรายงาน Discrepancy / Pending Log (UC10 Alternative 3a; ASM-06)
- `POST /api/reports/export` รับ `{reportType, format, from, to}` และสร้างไฟล์ PDF หรือ XLSX ที่ตรงกับ Dashboard เพื่อให้เจ้าของร้านส่งออกได้ทันที (UC10 Main Flow 4; ASM-05)
- หน้าจอรายงานยอดขายและการเงิน: แสดงปุ่ม Date Range Picker, สรุปยอดรวม, รายละเอียดตามช่องทางชำระเงิน, ค่าธรรมเนียม, ยอดสุทธิ, และสินค้าตัดสต๊อก (UC10 Main Flow 1-4; ASM-01, ASM-02, ASM-03, ASM-04, ASM-05)
- หน้าจอ Discrepancy / Pending Log: แสดงรายการที่ไม่ตรงกับ Statement ธนาคาร พร้อมสถานะการติดค้างหรือรอการยืนยันจาก Payment Gateway (UC10 Alternative 3a; ASM-06)

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี CON ID ใน spec | ไม่มีข้อจำกัดเชิงเทคนิคหรือข้อบังคับด้านผลิตภัณฑ์ที่ต้องใช้ใน plan | ยังไม่ได้ใช้ เพราะ spec ไม่มี CON |
| ไม่มี DOM ID ใน spec | ไม่มีข้อจำกัดด้านข้อมูลหรือการจัดเก็บข้อมูลเฉพาะที่ต้องใช้ | ยังไม่ได้ใช้ เพราะ spec ไม่มี DOM |
| ไม่มี IF ID ใน spec | ไม่มีข้อกำหนด interface หรือการเชื่อมต่อกับระบบภายนอกที่จำเป็นต้องกำหนดในแผนนี้ | ยังไม่ได้ใช้ เพราะ spec ไม่มี IF |

## 7. ลำดับงาน
1. กำหนดโครงสร้างข้อมูลรอบรายงานและเงื่อนไขช่วงเวลาเพื่อให้ Date Range Picker และเงื่อนไขปิดกะประจำวันมีความชัดเจนก่อนเริ่มประมวลผล (UC10 Main Flow 1-2; ASM-01)
2. สร้าง Reporting Aggregation API สำหรับคำนวณยอดขายรวม จำแนกตามช่องทางชำระเงิน พร้อมคำนวณค่าธรรมเนียมและยอดรับสุทธิแบบที่ต้องแม่นยำ 100% (UC10 Main Flow 3; ASM-02, ASM-04)
3. สร้าง engine สำหรับคำนวณยอดตัดสต๊อกจากยอดขายที่สำเร็จและตาม BOM เพื่อให้ปริมาณและรายการวัตถุดิบถูกหักลบจากคลังจริง (UC10 Main Flow 3; ASM-03)
4. สร้างหน้าจอ Dashboard สำหรับแสดงผลสรุปยอดขายรวม, รายละเอียดตามช่องทางชำระเงิน, ค่าธรรมเนียม, ยอดสุทธิ, และยอดตัดสต๊อก (UC10 Main Flow 3; ASM-02, ASM-03, ASM-04, ASM-05)
5. สร้างฟังก์ชันส่งออกไฟล์ PDF / Excel (.xlsx) ในรูปแบบตารางมาตรฐานสำหรับงานบัญชี พร้อมแน่ใจว่าเลขที่แสดงตรงกับ Dashboard (UC10 Main Flow 4; ASM-05)
6. สร้างรายงาน Discrepancy / Pending Log และเก็บข้อมูลที่ไม่ตรงกับ Statement ธนาคารไว้โดยไม่ลบหรือยกเลิกรายการ (UC10 Alternative 3a; ASM-06)
7. ทดสอบความถูกต้องของข้อมูลจาก API, Dashboard, และ export file สำหรับช่วงเวลาและทุกช่องทางชำระเงินที่เกี่ยวข้อง (UC10 Main Flow 2-4; ASM-01-06)
8. ตรวจสอบความครบถ้วนของ diff และเอกสาร traceability ก่อนย้ายไปสู่การสร้างแผนต่อในระดับรายละเอียดพัฒนา (UC10 Main Flow 1-4; Alternative 3a; ASM-01-06)

## 8. สิ่งที่ยังไม่ทำ
ไม่มี Open Questions ใน spec ขณะนี้ จึงไม่ต้องคัดลอกคำถามใด ๆ มาไว้ที่นี่

ส่วนที่ยังไม่สร้างจนกว่าจะมีคำตอบเพิ่มเติม:
- รูปแบบ exact payload และ schema ของ Reporting Aggregation API หากทีมต้องการให้มี contract ที่แน่นขึ้นกว่าทราบตอนนี้
- รายละเอียดความละเอียดของ export template สำหรับ PDF/XLSX ในแต่ละรายงานบัญชี หากทีมต้องการ template เฉพาะสำหรับสาขา/ช่วงเวลาหรือมี branding ของร้าน
- กฎและ threshold การถือว่าผิดพลาด “ไม่ตรงกับ Statement ธนาคาร” เป็นรายการ Discrepancy / Pending Log อย่างชัดเจน หากต้องมีการจัดกลุ่มตามสาเหตุหรือความสำคัญเพิ่มเติม

ส่วนเหล่านี้ยังไม่สร้างจนกว่าทีมจะให้คำตอบเพิ่มเติม เพราะ spec ปัจจุบันยังไม่ได้ระบุรายละเอียดเชิง technical contract หรือ template แบบละเอียดพอสำหรับการพัฒนาเชิงระบบจริง

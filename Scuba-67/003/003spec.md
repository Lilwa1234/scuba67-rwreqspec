# Use Case Specification: UC03 - Process Dynamic QR Payment

* **Use Case ID:** UC03[cite: 5]
* **Use Case Name:** ชำระเงินด้วย Dynamic QR Code (Process Dynamic QR Payment)[cite: 5]
* **Actor หลัก:** แคชเชียร์ (Cashier)[cite: 5]
* **Actor รอง:** ลูกค้า (Customer), ระบบชำระเงินภายนอก (Payment Gateway / Bank API)[cite: 5]
* **Pre-condition:** แคชเชียร์สรุปรายการออร์เดอร์และกดเลือกช่องทางชำระเงินผ่าน QR Code[cite: 5]
* **Post-condition:** ระบบบันทึกสถานะการชำระเงินสำเร็จ ลิ้นชักเก็บเงินไม่เปิด และพิมพ์ใบเสร็จรับเงิน[cite: 5]
* **Status:** Draft v2 | Updated: 2026-10-01

## Assumptions
* **ASM-01:** หากระบบไม่ได้รับ Webhook ยืนยันจาก Gateway ภายใน 3 นาที จะปรับสถานะเป็น "Pending / รอยืนยันจากธนาคาร" และแสดงแถบสีส้มบนหน้าจอ POS พร้อมให้แคชเชียร์กดปุ่ม "ตรวจสอบยอดเงิน (Re-check)" เพื่อสอบถามสถานะอีกครั้ง
* **ASM-02:** แคชเชียร์สามารถกดปุ่ม "เปลี่ยนเป็นเงินสด" หรือยกเลิก QR Code ได้ทันที ระบบจะตัดขั้นตอน QR และสลับไปคำนวณเงินทอนตามปกติ โดยป้องกันไม่ให้เกิดบิลซ้ำซ้อน
* **ASM-03:** ระบบสร้าง Dynamic QR Code ที่ล็อกยอดเงินตรงกับบิลสุทธิ 100% โดยลูกค้าไม่ต้องพิมพ์ยอดเอง หากยอดเงินมีความผิดปกติจะไม่ปิดออร์เดอร์ และจะถูกส่งเข้าบันทึกตรวจสอบ (Discrepancy / Pending Log)
* **ASM-04:** พิมพ์ใบเสร็จรับเงินเฉพาะเมื่อระบบได้รับ Webhook ยืนยันสถานะ "ชำระเงินสำเร็จ" เท่านั้น
* **ASM-05:** ระบบมี 3 สถานะสำหรับการแสดงผลบนจอ ได้แก่ รอชำระเงิน (Loading/QR Active), ชำระเงินสำเร็จ, และรอยืนยันจากธนาคาร (Pending สีส้ม เมื่อยอดเงินยังไม่เข้าภายในเวลาที่กำหนด)
* **ASM-06:** หากจอแสดงผลสำหรับลูกค้า (Customer Facing Display) ขัดข้อง แคชเชียร์สามารถสังเกตสถานะการรอชำระบนหน้าจอ POS ได้โดยตรง หรือเลือกกดยกเลิก QR เพื่อสลับไปรับชำระเป็นเงินสดแทน
* **ASM-07:** ระบบบันทึกข้อมูลการชำระเงินลงตาราง `payment_logs` ครบทุกธุรกรรม โดยเก็บหมายเลขออร์เดอร์, ยอดเงิน, Ref ID, สถานะ, ข้อมูลตอบกลับจากเกตเวย์ และเวลา `created_at` เพื่อใช้ตรวจสอบย้อนหลัง

## Main Flow (ลำดับขั้นตอนปกติ)
1. แคชเชียร์เลือกวิธีชำระเงินเป็น "QR Code สแกนจ่าย"[cite: 5]
2. ระบบส่งยอดรวมสุทธิไปยัง Payment Gateway เพื่อสร้าง Dynamic QR Code ที่ล็อกยอดเงินตรงกับบิลสุทธิ 100% โดยอัตโนมัติ และกำหนด Ref ID สำหรับตรวจสอบธุรกรรม[cite: 5]
3. หน้าจอแสดงผลสำหรับลูกค้า (Customer Facing Display) แสดงภาพ QR Code พร้อมยอดเงิน และแสดงสถานะ "รอชำระเงิน (Loading/QR Active)"[cite: 5]
4. ลูกค้าสแกนและยืนยันการโอนเงินผ่าน Mobile Banking[cite: 5]
5. หากยังไม่มี Webhook ยืนยันภายใน 3 นาที ระบบปรับสถานะเป็น "Pending / รอยืนยันจากธนาคาร" และแสดงแถบสีส้มพร้อมให้แคชเชียร์กด "ตรวจสอบยอดเงิน (Re-check)" เพื่อสอบถามสถานะไปยัง Gateway ซ้ำอีกครั้ง[cite: 5]
6. เมื่อระบบ Payment Gateway ส่งสัญญาณยืนยัน (Webhook) มายังเครื่อง POS แบบเรียลไทม์ ระบบจะปรับสถานะเป็น "ชำระเงินสำเร็จ"[cite: 5]
7. หน้าจอ POS แสดงสถานะ "ชำระเงินสำเร็จ" และพิมพ์ใบเสร็จรับเงินเฉพาะเมื่อได้รับ Webhook ยืนยันสถานะสำเร็จแล้ว เท่านั้น จากนั้นระบบจะปิดออร์เดอร์โดยอัตโนมัติ[cite: 5]

## Alternative / Exception Flows (ขั้นตอนทางเลือก / กรณีข้อผิดพลาด)
* **4a. ลูกค้าเปลี่ยนใจชำระเป็นเงินสด:** แคชเชียร์สามารถกดปุ่ม "เปลี่ยนเป็นเงินสด" หรือยกเลิก QR Code ได้ทันที ระบบจะตัดขั้นตอน QR เพื่อสลับไปคำนวณเงินทอนตามปกติ และป้องกันไม่ให้เกิดบิลซ้ำซ้อน[cite: 5]
* **5a. สัญญาณตอบรับจากเครือข่ายล่าช้า / ไม่มี Webhook ภายใน 3 นาที:** ระบบเปลี่ยนสถานะเป็น "Pending / รอยืนยันจากธนาคาร" (สีส้ม) และแคชเชียร์สามารถกดปุ่ม "ตรวจสอบยอดเงิน (Re-check)" เพื่อสั่งให้ระบบสอบถามสถานะไปยัง Gateway ซ้ำโดยตรง[cite: 5]
* **5b. ยอดเงินมีความผิดปกติหรือไม่ตรงกับบิลสุทธิ:** ระบบจะไม่ปิดออร์เดอร์และจะส่งข้อมูลเข้าบันทึกตรวจสอบ (Discrepancy / Pending Log) เพื่อให้ฝ่ายที่เกี่ยวข้องตรวจสอบต่อไป[cite: 5]

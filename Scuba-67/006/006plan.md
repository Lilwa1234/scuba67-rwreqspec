# แผนทางเทคนิค: UC06 - สลับสถานะสินค้าหมดด่วน

## 1. สรุปแนวทาง
1. ฟีเจอร์นี้ช่วยให้แคชเชียร์สามารถกดค้างบนเมนูที่ต้องการ 1 วินาที เพื่อเปิด Quick Action Toggle แล้วสลับสถานะเป็น "หมด" สำหรับเมนูนั้นเท่านั้น (UC06 Main Flow 1-2, ASM-01, ASM-03)
2. หลังจากสลับสถานะ ระบบจะปิดใช้งานเมนูในหน้าจอขายของเครื่อง POS ทุกเครื่อง ทำให้คลิกสั่งซื้อไม่ได้ และแจ้งสถานะไปยังแอปพลิเคชันของเจ้าของร้านทันทีผ่าน WebSocket Broadcast (UC06 Main Flow 3, ASM-02, ASM-06)
3. เมนูที่ถูกปิดจะเปลี่ยนเป็นสีเทาและแสดงป้ายข้อความ "หมด" ทันที โดยไม่ต้องสลับไปใช้งานแอปอื่น (UC06 Main Flow 4, ASM-03)
4. เมื่อวัตถุดิบพร้อมขายอีกครั้ง แคชเชียร์กดค้างที่เมนูเดิมแล้วสลับกลับเป็น "พร้อมขาย" เพื่อคืนสถานะปกติทันทีและให้กดสั่งซื้อได้ทันที (UC06 Alternative Flow 2a, ASM-04, ASM-05)
5. การพัฒนาใช้แนวทางแยกแยะระหว่าง interface ของหน้าจอ POS, API สำหรับบันทึกสถานะเมนู, และ broadcast event เพื่อ sync ระหว่างเครื่องทุกเครื่องให้สอดคล้องกับกระบวนการปิดชั่วคราวระหว่างวัน (UC06 Main Flow 1-4, Alternative Flow 2a)

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าจอ POS และ Quick Action Toggle | ทีมเลือกเอง ไม่ได้มาจาก spec | spec ไม่ระบุ framework ของ UI แต่ฟีเจอร์นี้ต้องมีการกดค้างบนเมนูและสวิตช์สถานะทันที |
| Python FastAPI สำหรับหลังบ้านและ API สถานะเมนู | ทีมเลือกเอง ไม่ได้มาจาก spec | spec ไม่ระบุ framework แต่ต้องรองรับ event sync ระหว่าง POS และเจ้าของร้าน |
| WebSocket Broadcast | ASM-06 | ใช้สำหรับซิงก์สถานะเมนูไปยังเครื่อง POS ทุกเครื่องและแอปเจ้าของร้านแบบเรียลไทม์ |
| โครงสร้างสถานะเมนูแบบ boolean/enum | ASM-01, ASM-02, ASM-04, ASM-05 | ใช้เก็บสถานะ "available" และ "sold_out" เพื่อปิดชั่วคราวและกลับเป็นพร้อมขายได้อีกครั้ง |
| Long Press / Click Hold interaction | ASM-03 | ใช้เปิด Quick Action Toggle เมื่อผู้ใช้กดค้างบนการ์ดเมนู 1 วินาที |
| Event log / status history | ASM-06 | ช่วยตรวจสอบว่าเมนูเปลี่ยนสถานะจากพร้อมขายเป็นหมดเมื่อใด และสลับกลับเมื่อใด |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับข้อกำหนด |
|---|---|---|
| MenuItem | menu_id, item_name, image_url, category_id, is_active, sold_out, updated_at | UC06 Main Flow 2-4; ASM-01, ASM-02, ASM-04, ASM-05 |
| MenuDisplayState | menu_id, pos_device_id, is_available, display_label, color_state, last_updated_at | UC06 Main Flow 3-4; ASM-02, ASM-06 |
| MenuStatusEvent | event_id, menu_id, previous_status, new_status, triggered_by, occurred_at | UC06 Main Flow 2-4, Alternative Flow 2a; ASM-04, ASM-06 |
| OwnerAlertEvent | alert_id, menu_id, event_type, sent_at, status | UC06 Main Flow 3; ASM-06 |

ข้อมูลที่เก็บจะเน้นเพียงสถานะเมนูและ event history ที่จำเป็นสำหรับการปิดชั่วคราวและการซิงก์ระหว่างเครื่องเท่านั้น ไม่มีการจัดเก็บข้อมูลส่วนบุคคลหรือข้อมูลการชำระเงินตามฟีเจอร์นี้

## 4. API / หน้าจอ

- `GET /api/pos/menu/{id}` ส่งกลับข้อมูลเมนูพร้อมสถานะปัจจุบันและสถานะการขายเพื่อแสดงบนหน้าจอขาย (UC06 Main Flow 1, 3; ASM-01, ASM-02)
- `PATCH /api/pos/menu/{id}/sold-out` รับ `{ menuId, soldOut: true }` และส่งกลับข้อมูลเมนูที่อัปเดตเป็นสถานะหมด พร้อมบันทึก event log (UC06 Main Flow 2-4; ASM-01, ASM-05)
- `PATCH /api/pos/menu/{id}/restore` รับ `{ menuId, soldOut: false }` และคืนสถานะเมนูเป็นพร้อมขายทันที พร้อมบันทึก event log (UC06 Alternative Flow 2a; ASM-04)
- `GET /api/pos/menu-status` ส่งกลับรายการเมนูที่มีสถานะปิดชั่วคราวเพื่อใช้กับหน้า POS 或 admin dashboard (UC06 Main Flow 3; ASM-02, ASM-06)
- `WS /ws/menu-status` ส่งสัญญาณ WebSocket Broadcast เมื่อสถานะเมนูเปลี่ยน พร้อมข้อมูล `{ menuId, soldOut, broadcastAt }` ไปยังทุกเครื่องและแอปเจ้าของร้าน (UC06 Main Flow 3; ASM-06)
- หน้าจอ POS: แสดงการ์ดเมนูพร้อมปุ่มภาพและ Quick Action Toggle/Long Press ให้ผู้ใช้กดค้าง 1 วินาทีเพื่อสลับสถานะ (UC06 Main Flow 1-2; ASM-03)
- หน้าจอเจ้าของร้าน: แสดงการแจ้งเตือนเมื่อมีเมนูเปลี่ยนสถานะและสามารถเห็นสถานะ real-time ของเมนูที่ถูกปิดชั่วคราว (UC06 Main Flow 3; ASM-06)

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี CON ID ใน spec | ไม่มีข้อจำกัดด้านเทคนิคหรือสถาปัตยกรรมที่ต้องใช้ภายในแผนนี้ | ยังไม่ได้ใช้ เพราะ spec ไม่มี CON |
| ไม่มี DOM ID ใน spec | ไม่มีข้อจำกัดด้านข้อมูลหรือการจัดเก็บข้อมูลที่ต้องใช้ | ยังไม่ได้ใช้ เพราะ spec ไม่มี DOM |
| ไม่มี IF ID ใน spec | ไม่มีข้อกำหนด interface หรือการเชื่อมต่อภายนอกที่ต้องใช้ใน plan | ยังไม่ได้ใช้ เพราะ spec ไม่มี IF |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| ไม่มี AC ID ใน spec | `test_UC06_main_flow_toggle_sold_out` | ทดสอบว่าเมื่อแคชเชียร์กดค้าง 1 วินาทีบนเมนูที่เลือก ระบบเปิด Quick Action Toggle และเมื่อลองสลับสถานะ ร้านจะปิดเมนูที่เลือกเท่านั้น ให้คลิกสั่งซื้อไม่ได้ และ UI เปลี่ยนเป็นสีเทา + ป้าย "หมด" |
| ไม่มี AC ID ใน spec | `test_UC06_restore_flow_available_again` | ทดสอบว่าเมื่อต้องการขายอีกครั้ง แคชเชียร์กดค้างที่เมนูเดิม และสลับกลับเป็น "พร้อมขาย" ระบบคืนสีปกติและให้สั่งซื้อได้ทันที โดยไม่ต้องรออนุมัติ |
| ไม่มี AC ID ใน spec | `test_UC06_ws_broadcast_all_pos` | ทดสอบว่าเมื่อสถานะเมนูเปลี่ยน ตัวอย่าง WebSocket payload ถูกส่งและ POS เครื่องอื่น ๆ รับข้อมูลแล้วอัปเดตสถานะเมนูพร้อมกันแบบ real-time |

> หมายเหตุ: UC06 ใน spec ปัจจุบันมีอยู่เฉพาะ Main Flow / Alternative Flow และไม่ระบุ AC ID อย่างเป็นทางการ จึงไม่สามารถตั้งชื่อ test ตาม AC ID ได้อย่างครบถ้วนในตอนนี้

## 7. ลำดับงาน

1. กำหนดโครงสร้างข้อมูลเมนูและ status state สำหรับ `available` / `sold_out` ให้สอดคล้องกับ UC06 Main Flow และ Alternative Flow (UC06 Main Flow 1-4; ASM-01, ASM-02, ASM-05)
2. สร้าง API หลังบ้านสำหรับปิดเมนูและเปิดเมนูใหม่ พร้อมบันทึก `MenuStatusEvent` และ `OwnerAlertEvent` เพื่อใช้ตรวจสอบเหตุการณ์ย้อนหลัง (UC06 Main Flow 2-4; ASM-04, ASM-06)
3. สร้าง interaction บนหน้าจอ POS สำหรับ long press 1 วินาที เพื่อเปิด Quick Action Toggle และแสดงสวิตช์สถานะของเมนูที่เลือก (UC06 Main Flow 1-2; ASM-03)
4. สร้างสมมติฐาน UI state เมื่อเมนูถูกปิด: สีเทา + ป้าย "หมด" + ปุ่มกดสั่งซื้อปิดใช้งาน พร้อมตรวจว่ามีผลเฉพาะเมนูที่เลือกเท่านั้น (UC06 Main Flow 3-4; ASM-01, ASM-02)
5. สร้าง WebSocket broadcast event เพื่อส่งสถานะเมนูไปยังเครื่อง POS ทุกเครื่องและแอปเจ้าของร้านทันที เมื่อมีการ toggle (UC06 Main Flow 3; ASM-06)
6. สร้าง logic สำหรับสลับกลับเป็นพร้อมขายทันทีเมื่อมีการกดค้างที่เมนูเดิมและกดสวิตช์กลับ (UC06 Alternative Flow 2a; ASM-04, ASM-05)
7. ทดสอบความถูกต้องของสถานะเมนูในทุกเครื่อง POS และการส่ง event ไปยังเจ้าของร้าน พร้อมตรวจว่าตัวเลือกเมนูอื่นไม่ถูกปิดโดยอัตโนมัติ (UC06 Main Flow 3, Alternative Flow 2a; ASM-01, ASM-02, ASM-06)
8. ทดสอบกรณีเชื่อมต่อ network ไม่เสถียร เพื่อยืนยันว่า event status สุดท้ายยังคงสอดคล้องกับสถานะปัจจุบันบนแต่ละ POS (UC06 Main Flow 3; ASM-06)

## 8. สิ่งที่ยังไม่ทำ

ไม่มี Open Questions ใน spec หลังจาก Clarify แล้ว ขณะนี้ไม่มีข้อข้องใจที่ต้องรอคำตอบเพื่อเริ่มพัฒนา

ส่วนที่ยังไม่สร้างจนกว่าจะมีคำตอบเพิ่มเติม:
- รูปแบบ payload ของ WebSocket Broadcast ที่แน่ชัดสำหรับเครื่อง POS ทุกเครื่องและแอปเจ้าของร้าน หากต้องใช้โครงสร้าง payload ที่มี field เพิ่มสำหรับ monitoring
- มาตรฐานการ retry / fallback เมื่อสัญญาณเครือข่ายขัดข้องระหว่างส่งสถานะระหว่างเครื่อง หากทีมต้องการให้ระบบพยายามส่งซ้ำหรือแสดงข้อความปรับสถานะด้วยตัวเอง

ส่วนเหล่านี้ยังไม่สร้างจนกว่าทีมจะให้ข้อมูลเพิ่มเติม เพราะ spec ปัจจุบันไม่ได้ระบุรายละเอียด technical contract ของ broadcast หรือเงื่อนไข fallback แบบละเอียดมากพอสำหรับการพัฒนาเชิงระบบจริง
